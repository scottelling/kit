# Design and Ship Project

Own the path from brief to live proof. Speak to the user in plain language and keep implementation details out of the public experience unless requested.

## Work in this order

1. Discover the project authority before changing files. Read the repository instructions, locked conventions, design system, deployment records, and current product.
2. Convert the request into a short project receipt: audience, job, product type, required surfaces, proof, constraints, and definition of done. Mark uncertain facts as assumptions; never invent business proof.
3. Choose one visual thesis and one structural signature. Build the foundations—type, color roles, spacing, shape, depth, motion, voice, and interaction states—before expanding pages.
4. Build the complete product journey, including loading, empty, error, success, disabled, focus, keyboard, reduced-motion, and responsive states where relevant.
5. Test the real experience in a browser at 320, 375, 414, 768, and desktop widths. Fix overflow, wrapping, contrast, touch, focus, console, and visual-quality failures.
6. Run the repository’s full checks. Deploy through its established release path, verify the live domain, and repeat critical interactions on production.
7. Report only the outcome, visible capabilities, live location, and proof in plain language.

## Purple Rain standard

- Keep the current object and next action obvious.
- Use accent for selection, focus, progress, and the primary decision.
- Prefer solid tonal surfaces, crisp borders, and directional depth.
- Do not use glass, backdrop blur, translucent decoration, glow, gradients, ambient blobs, floating-card lifts, or resting animation loops.
- Keep touch targets at least 44 pixels and focus immediate and visible.
- Animate only when movement explains origin, state, progress, or consequence; provide reduced-motion behavior.
- Preserve user work and existing project conventions. Ask only when a missing choice would materially change the outcome or authorize a new external action.

## Completion contract

Do not call the project finished until the requested product is complete, the browser experience passes, the production build passes, deployment succeeds, and the live version is verified. If a safe in-scope route remains, continue working.
